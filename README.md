# Video QA Challenge - Android E2E Tests

Android end-to-end test automation for the deterministic Video QA Challenge
application. The suite covers consent, the video catalogue, video details, and
the player state machine.

## Solution Overview

The project uses TypeScript, WebdriverIO 9, Appium, UIAutomator2, and Mocha.
Appium and WebdriverIO were preferred by the assignment and provide a black-box
approach suitable for a final application build. The Screen Object architecture
keeps selectors and screen actions separate from user-facing specifications.

The test strategy began with manual exploratory testing, supported by AI, to
produce the requirements and risk-based test plan. Scenarios were then
implemented iteratively by screen and requirement, following the repository
rules in `Agents.md`.

## Prerequisites

- Node.js 25.9.0 and npm 11.12.1
- Android SDK and an Android emulator or device
- Android Emulator with Android 16
- An Android device available as `emulator-5554`, or equivalent values supplied
  through `.env.local`
- The APK at `apps/VideoQAChallenge-debug.apk`

Appium is installed with the project dependencies and started automatically by
the WebdriverIO Appium service. A separate local Appium installation or server
is not required.

## Running the Tests

1. Install project dependencies:

   ```bash
   npm install
   ```

2. Start the Android emulator or connect a supported Android device.

3. Build the TypeScript project:

   ```bash
   npm run build
   ```

4. Run the Android end-to-end suite:

   ```bash
   npm run run.android.tests
   ```

The Android capabilities are configured in
`test/config/android.local.conf.ts`. The suite uses UIAutomator2 and exact
accessibility-ID matching through `appium:disableIdLocatorAutocompletion`.
If dependency installation fails because the Appium service dependencies cannot
be installed, temporarily comment out the `services` section in
`android.local.conf.ts`. This disables automatic Appium startup, so the test
run must use an externally running Appium server.

## Running the Tests on GitHub

The suite can also run in GitHub Actions through the manually triggered
`Android E2E Tests` workflow.

1. Open the repository on GitHub and select the **Actions** tab.
2. Select **Android E2E Tests** from the workflow list.
3. Click **Run workflow**.
4. Select the branch to test and click **Run workflow** to start the run.
5. Open the resulting workflow run to review the Android test summary, Appium
   log artifact, and published Allure report.

The workflow checks out the selected branch, enables KVM, restores the npm
cache, installs dependencies with `npm ci`, and starts an Android 16
Google APIs Pixel 7 Pro emulator. It runs `npm run run.android.tests`, publishes
the JUnit results in the Actions run, uploads the Appium log, generates the
Allure report, and deploys that report to GitHub Pages.

## Allure Report

The test run writes results to `allure-results/`. Generate and open the report
after a run:

```bash
allure generate allure-results
allure open
```

The report generated by the GitHub Actions workflow is published at
[ricardorlg.github.io/dpg-interview](https://ricardorlg.github.io/dpg-interview/).

## Future Work

- Integrate Sauce Labs or BrowserStack to parallelize tests over a broader
  Android device and Android-version matrix. Android 16 is the default because
  it is convenient and repeatable locally and in CI; a device farm would avoid
  the operational cost of running multiple emulator versions concurrently in
  GitHub-hosted CI.
- Add an Android-version workflow parameter, keeping Android 16 as the default.
- Preserve Allure execution history between GitHub Actions runs to expose trends
  in the published report.
- Add iOS selectors and configuration while reusing shared scenarios and test
  logic.
- Implement the remaining planned scenarios documented in
  [TEST_PLAN.md](TEST_PLAN.md).
